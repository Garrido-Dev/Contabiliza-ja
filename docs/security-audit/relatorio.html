Nota Metodológica de Mapeamento de Stack

O projeto Contabiliza Já não possui servidor de backend intermediário dedicado (Node.js, Express, Python ou Java). Todas as operações de leitura, escrita e exclusão ocorrem diretamente do cliente web React para a nuvem da Google via Firebase SDK Modular. Consequentemente, cada uma das 5 categorias da auditoria foi mapeada estritamente para essa arquitetura:

  • 1. Banco Sem Tranca: Mapeado para Security Rules do Firestore / Storage e associação correta de userId nos documentos.
  • 2. Permissão Definida no Navegador: Mapeado para bloqueios de UI/Planos (ex: módulo "Pro" em Documents.jsx) sem validação no backend/BaaS.
  • 3. IDOR: Mapeado para comandos diretos de updateDoc, deleteDoc e rotas públicas de getDoc sem validação de titularidade.
  • 4. Chaves Expostas: Mapeado para configuração estática do Firebase no bundle, variáveis .env ignoradas e histórico git.
  • 5. Inputs Sem Tratamento (XSS): Mapeado para URLs dinâmicas e links controlados por usuário no DOM (href).
Classificação: Confidencial / Interno Escopo: Código-fonte completo, CI/CD, Bundle compilado e Histórico Git

A auditoria identificou vulnerabilidades arquiteturais severas resultantes do uso direto do Firebase Firestore e Storage no cliente web sem versionamento ou garantia de regras de segurança rígidas (Security Rules). 3. Achados Detalhados da Auditoria

Achado 1 — Ausência Completa de Regras de Segurança no Banco (Firestore / Storage Rules)
Severidade: CRÍTICA
Categoria: 1 (Banco Sem Tranca)
Arquivo: Raiz do repositório (firestore.rules e storage.rules inexistentes)
Trecho:
// src/services/firebase.js:28-36
export const db = getFirestore(app);
export const auth = getAuth(app);
export const storage = getStorage(app);
// NENHUM arquivo firestore.rules ou storage.rules presente no repositório.
Por que é explorável:

Em arquiteturas BaaS, o cliente fala diretamente com a infraestrutura na nuvem. Sem Security Rules versionadas e declaradas, o isolamento depende da configuração remota do Firebase. Se as regras estiverem em modo padrão ou permissivo, qualquer atacante com as credenciais públicas pode consultar e deletar documentos de todos os usuários omitindo o filtro where('userId', '==', user.uid) via script ou DevTools.

Exploit Path:
[Atacante abre console do browser ou Node.js com a config do Firebase] → await getDocs(collection(db, 'clients')) (sem cláusula where) → [Recebe todos os dados cadastrais, faturamento e documentos de todos os clientes de todos os usuários da aplicação].
Condição de explorabilidade: Regras padrão do Firestore permissivas ou em modo teste.
Sugestão de correção: Criar imediatamente firestore.rules impondo que request.auth.uid == resource.data.userId para leitura e escrita, e vincular o deploy no CI/CD.

Sugestão de correção: Implementar regras no Firestore que impeçam escrita e deleção caso request.auth.uid != resource.data.userId.
